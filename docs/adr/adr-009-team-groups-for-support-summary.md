# ADR: Team Groups for the Support Summary

**Status:** Proposed

## Context

The Support Summary page (`/summary`) describes what support saw across a date window for **every**
tenant. Engagement teams meet tenants per *area* — a client's grouping of several tenant teams (e.g.
ADDDS) — and want to open those meetings with the same summary focused on that area. Today the page
can only show one team's tickets indirectly (the Top Teams card), never a group's narrative.

The bot is open source and deployed at several clients. Each has its own grouping (area, domain,
tribe, business unit) and its own way of discovering tenant teams (static config, the core-platform
Kubernetes fetcher, generic CEL over Kubernetes resources). Nothing in the codebase models a level
above tenant teams.

The word "area" is already taken twice: the summary's **Top Support Areas** card is the classifier's
drivers dimension, and `summary-area:` is the configuration prefix of the summary feature. Separately,
`teams.groups` (`GroupRef`) means identity-provider groups that team members are resolved from.

## Decision

Introduce **team groups**: named sets of tenant team codes that the Support Summary can be narrowed to.

### Configuration

```yaml
team-groups:
  display-name: Area            # the noun the UI shows; deployment-specific, default "Area"
  groups:
    - code: addds               # stable, URL-safe; appears in shareable links
      label: ADDDS
      team-codes: [payments-api, ledger, onboarding]
```

- **Generic name in code and config, deployment-chosen name in the UI.** "Team group" avoids both
  "area" clashes; each deployment calls them whatever its organisation does.
- **Static source behind a seam.** Groups come from configuration only (`StaticTeamGroupProvider`),
  behind a `TeamGroupProvider` interface so a later source (e.g. a Kubernetes namespace label or CEL
  expression) can be added without touching consumers.
- **Keyed on team codes**, the value stored on tickets (`ticket.team`), so groups work with every
  team provider and with retired teams' history.
- **Validation:** structural mistakes (blank display name or label, malformed or duplicate code, empty
  or repeated team codes) fail startup. A team code that is not a current tenant team only **warns** —
  retired codes legitimately stay on historical tickets, and dynamic team providers can drift.
- A team may belong to several groups.

### Behaviour

- `GET /summary?teamGroup=<code>` narrows every figure, the per-ticket reasons and the narrative to
  tickets attributed to the group's teams; an unknown code is a 400 (`SUMMARY_TEAM_GROUP_UNKNOWN`).
  No parameter keeps today's behaviour ("All").
- `GET /summary/team-groups` lists the groups and the display name, under the same roles as
  `/summary`. With no groups configured the UI hides its selector.
- **Classification is never narrowed.** The backfill and the shared `analysis` lock work on the whole
  window whatever group asked, so every ticket is classified once and switching group only costs the
  narrative.
- **Cache per (window, team group, prompt).** `summary_snapshot` gains `team_group` (`''` for the whole
  window — a NOT NULL sentinel, because NULLs are distinct in a unique constraint and would defeat
  `ON CONFLICT`). Existing rows become "All" unchanged.
- **Group fingerprint.** A group's fingerprint covers only the group's tickets — so another team's
  ticket closing does not regenerate every group's narrative — plus a digest of the group's label and
  members, so reconfiguring a group invalidates its narrative. The whole window's fingerprint is
  byte-identical to before, so no existing snapshot is regenerated by the upgrade.
- **Failures and refresh status** are remembered per (window, group); a group's failure does not block
  the whole window.
- **Resume payload.** A group refresh claims the lock with a new `team-group-window` payload type
  rather than an extra field on `window`, so a whole-window payload stays readable by earlier
  versions. A resumed group that is no longer configured is refreshed for the whole window.
- **Prompt unchanged.** The report sent to the model gains one `Scope:` line naming the group and its
  teams; the summary prompt is not versioned, because a new version would orphan every cached snapshot
  at every deployment.

### Not decided here

- Narrowing other pages (Tickets, Escalations, Stats) or the global "View as" selector by team group.
- A non-static group source.

## Consequences

### Positive

- Engagement meetings can open on a shareable link to one area's summary.
- No client-specific behaviour in code: deployments without groups see no change.
- Switching group is quick once a window is classified; only the narrative is generated.

### Negative

- One LLM call per (window, group) actually viewed, and one snapshot row each.
- A group refresh waits behind any in-flight refresh, because the lock is global.
- A group's totals do not sum to the whole window's (unattributed and "Not a Tenant" tickets belong to
  no group; overlapping groups double-count), which the user guides explain.
- Rolling back past `V41` needs the unique key restored by hand (see the Support Summary runbook).
- A renamed team code splits a team's history; operators list both codes in the group.
- The model may still generalise beyond the group despite the `Scope:` line; a scope-aware prompt
  version is the follow-up if it does.

## Alternatives considered

- **Extending `SummaryWindow` with the group.** Rejected: the window type is what the backfill and lock
  use, and keeping it group-free shows in the types which paths are narrowed.
- **A nullable `team_group` column.** Rejected: NULLs are distinct in a unique constraint, so
  `ON CONFLICT` would never match the "All" row (`NULLS NOT DISTINCT` needs Postgres 15+).
- **A separate snapshot table for groups.** Simpler rollback, but a second table and a branch in every
  snapshot query for the same data.
- **An `area` attribute on each team provider.** More automatic, but every fetcher would need changes
  and the core-platform fetcher has no obvious source; left for a later `TeamGroupProvider`.
- **Groups managed in the UI/database.** More flexible, but a much larger surface (CRUD, permissions)
  than the need justifies today.
