# ADR: Team Groups for the Support Summary

**Status:** Proposed

## Context

The Support Summary page (`/summary`) describes what support saw across a date window for **every**
tenant. Tenant teams can be organised into *areas* — groupings of several tenant teams (e.g.
Payments) — and it is useful to see the same summary focused on one area. Today the page
can only show one team's tickets indirectly (the Top Teams card), never a group's narrative.

The bot can run in many installations, each of which may group its teams differently (area, domain,
tribe, business unit) and discover them differently (static config, the core-platform Kubernetes
fetcher, generic CEL over Kubernetes resources). Nothing in the codebase models a level
above tenant teams.

The word "area" is already taken twice: the summary's **Top Support Areas** card is the classifier's
drivers dimension, and `summary-area:` is the configuration prefix of the summary feature. Separately,
`teams.groups` (`GroupRef`) means identity-provider groups that team members are resolved from.

## Decision

Introduce **team groups**: sets of tenant teams that the Support Summary can be narrowed to, built
from a **team attribute**. Tenant teams with the same value for the attribute form one group.

### Configuration

```yaml
team-groups:
  display-name: Area   # the noun the UI shows; per installation, default "Area"
  attribute: area      # the team attribute whose value names a team's group
```

- **Generic name in code and config, installation-chosen name in the UI.** "Team group" avoids both
  "area" clashes; each installation calls them whatever its organisation does.
- **Built from team attributes.** Team providers already expose attributes on teams: the k8s-generic
  fetcher reads them from each team's resource with CEL, and static teams list them in config. The
  grouping is then kept where the teams are defined rather than in a second list that would need to
  be kept in step. The provider sits behind a `TeamGroupProvider` interface, so consumers don't
  depend on where groups come from.
- **Codes derived from values.** A group's code, used in shareable links, is its value reduced to
  lowercase ASCII letters, digits and hyphens, at most 64 characters; values that differ only in
  case, accents, or the spaces and punctuation between words share a group, and the different
  spellings are logged. The label is the value itself.
- **Keyed on team codes.** A group's members are team codes, the value stored on tickets
  (`ticket.team`), so narrowing works the same with every team provider that sets the attribute.
- **Validation:** a blank display name or attribute name fails startup. No team carrying the
  attribute only **warns**, as do values that can't make a code; those teams join no group.
- A team belongs to at most one group.

### Behaviour

- `GET /summary?teamGroup=<code>` narrows every figure, the per-ticket reasons and the narrative to
  tickets attributed to the group's teams; an unknown code is a 400 (`SUMMARY_TEAM_GROUP_UNKNOWN`).
  No parameter keeps today's behaviour ("All").
- `GET /summary/team-groups` lists the groups and the display name, under the same roles as
  `/summary`. With no groups the UI hides its selector and shows no scope, so the page reads as
  before.
- **Classification follows the scope.** A group's refresh classifies only the group's own tickets;
  "All" classifies whatever in the window is still unclassified, including the tickets no group
  shows (no team, "Not a Tenant", or a team in no group). Results are stored per ticket and prompt,
  so each ticket is classified once per classification prompt, and a ticket that keeps failing is
  only retried by the scopes that report on it rather than by every group's. The shared `analysis`
  lock stays global.
- **Cache per (window, team group, prompt).** `summary_snapshot` gains `team_group` (`''` for the whole
  window — a NOT NULL sentinel, because NULLs are distinct in a unique constraint and would defeat
  `ON CONFLICT`). Existing rows become "All" unchanged.
- **Group fingerprint.** A group's fingerprint covers only the group's tickets — so another team's
  ticket closing does not regenerate every group's narrative — plus a digest of the group's label and
  members, so a change to its label or members invalidates its narrative. The whole window's fingerprint is
  byte-identical to before, so no existing snapshot is regenerated by the upgrade.
- **Failures and refresh status** are remembered per (window, group); a group's failure does not block
  the whole window.
- **Resume payload.** A group refresh claims the lock with a new `team-group-window` payload type
  rather than an extra field on `window`, so a whole-window payload stays readable by earlier
  versions. A resumed group that no longer exists is refreshed for the whole window.
- **Prompt unchanged.** The report sent to the model gains one `Scope:` line naming the group and its
  teams; the summary prompt is not versioned, because a new version would orphan every cached snapshot
  at every installation.

### Not decided here

- Narrowing other pages (Tickets, Escalations, Stats) or the global "View as" selector by team group.
- Keeping retired teams in their last group (see Negative).

## Consequences

### Positive

- A shareable link opens straight on one area's summary.
- No installation-specific behaviour in code: installations without groups see no change.
- Switching group is quick once the group's tickets are classified; only the narrative is generated.

### Negative

- One LLM call per (window, group) actually viewed, and one snapshot row each.
- The first visit to each group in a window waits for that group's tickets to be classified. Tickets
  in no group are only classified when "All" is viewed, or by a manual run.
- A group refresh waits behind any in-flight refresh, because the lock is global. While one runs,
  every viewer sees the summary as generating, including those whose cached summary is current;
  that was already true across windows, and groups make it more frequent.
- A group's totals do not sum to the whole window's (unattributed and "Not a Tenant" tickets belong to
  no group), which the user guides explain.
- Rolling back past `V41` needs the unique key restored by hand (see the Support Summary runbook).
- Groups follow the teams fetched at startup. A team that is no longer fetched leaves its group,
  taking its past tickets out of the group's summary, and a team that moves group takes its history
  with it. Keeping retired teams would need their last attributes stored, e.g. in the `team` table.
- Renaming a value changes the group's code, so old links fall back to every team and the group's
  narrative is regenerated.
- Installations whose team provider sets no attributes (the core-platform fetcher) have no groups.
- The model may still generalise beyond the group despite the `Scope:` line; a scope-aware prompt
  version is the follow-up if it does.

## Alternatives considered

- **Extending `SummaryWindow` with the group.** Rejected: the window (the period a summary covers)
  and the optional group narrowing it are separate concerns. `SummaryScope` pairs them, so "All" is a
  scope with no group rather than a window carrying a nullable group.
- **A nullable `team_group` column.** Rejected: NULLs are distinct in a unique constraint, so
  `ON CONFLICT` would never match the "All" row (`NULLS NOT DISTINCT` needs Postgres 15+).
- **A separate snapshot table for groups.** Simpler rollback, but a second table and a branch in every
  snapshot query for the same data.
- **Groups listed in configuration** (code, label and team codes per group). Works with every team
  provider and could keep retired teams, but it is a second list of teams to keep in step with the
  one the team provider already has, and it drifts as teams come and go.
- **Groups managed in the UI/database.** More flexible, but a much larger surface (CRUD, permissions)
  than the need justifies today.
