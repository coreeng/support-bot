## 1. Validate the approach on real tickets

- [ ] 1.1 Build the labelled set: take at least one month of closed tickets and have a support engineer give each of at least 150 of them one of the four classifications and, for documentation questions, the product area that should answer it. Add tickets until each classification has at least 15. Have a second support engineer label 30 of the same tickets independently and record how often the two agree. Keep the set out of the repository.
- [ ] 1.2 Draft the routing and classification prompts and run them over the labelled set against a local clone of a documentation repository, through the LLM provider the deployment is approved to send ticket text to. Label each message as tenant, support or bot, as design Decision 7 describes, and lay out the inputs and apply the checks of Decisions 2, 8 and 10 by script. Record the measures listed under Validation in `design.md`, and replace the cost and time estimates in the proposal's Impact with the measured ones.
- [ ] 1.3 Compare 1.2 with the targets under Validation in `design.md`. Build only when they are met; otherwise revise the prompts, `design.md` and the spec and repeat 1.2. Keep on record the share of tickets whose existing primary driver is Task Request or Product Temporary Issue, for a later decision on a pre-filter.

## 2. Documentation source boundary

- [ ] 2.1 Define the documentation source boundary of design Decision 2 in the analysis's package: opening a session or reporting the source unavailable, the session's version, `findContext(thread, budget)` with its four answers (pages, nothing covers it, not a documentation question, failed), the first three able to carry the distilled question, and the fingerprint. Add a stub source for tests that returns canned answers. Verify with unit tests, and add a test that fails when code outside a source's package refers to that package's types.
- [ ] 2.2 Add configuration properties under a new top-level `documentation-analysis` block for the settings listed in design Decision 6: the analysis's own at the top and each source's under `source`, with `enabled` off by default. Select the active source from `source.type`, and fail startup when the feature is enabled with an unknown source or one that lacks a setting it needs. Add the settings to `application.yaml`, the Helm values and schema, and `api/service/docs/configuration.md`.
- [ ] 2.3 Build the shared wrapping of model inputs that design Decision 10 describes, for the analysis and for sources: each part in its tags with the tag names removed from the data, instructions last. Verify with unit tests for a thread and a page that contain a tag name.

## 3. GitHub source

- [ ] 3.1 Add a method to `GitHubClient` that resolves a branch to its head commit and one that downloads the repository archive at a commit, implemented in `Hub4jGitHubClient`. Make the `GitHub` and `GitHubClient` beans available when the GitHub source is selected as well as when PR tracking uses a GitHub repository. Fail startup with a message naming the setting when the feature is enabled with the GitHub source and the `pr-review-tracking.github` block holds no usable credentials, whether or not PR tracking is on. Verify with unit tests, that a deployment with PR tracking off and this feature on starts, and that one with this feature on and no credentials does not.
- [ ] 3.2 Add the GitHub source's copy, refreshed when the run opens the source: fetch when absent or expired, skip the download when the head commit is unchanged, replace the copy only when complete, fall back to an expired copy when a fetch fails, and expose the commit and fetch time. Read the archive as a stream, write only regular files under the configured path with a configured extension, skip links and entries whose path is absolute or contains `..`, and fail the fetch over `max-copy-size` or `max-files`. Verify each scenario of the GitHub source spec's repository requirement with unit tests, including an archive with a link, with a `..` path, and over each limit.
- [ ] 3.3 Build the page index (path, title, description; path and first heading when frontmatter is absent) and the product-area grouping when a copy is loaded. Report the source as unavailable, with a clear error, when there is no product area or the root pages alone exceed the budget, and log a warning for an area that alone exceeds it. Verify with unit tests, including pages at the root of the documentation path, a repository with no areas, and oversized root pages.
- [ ] 3.4 Implement the boundary for the GitHub source, as design Decision 12 describes: the routing call over the page index and the thread, which distils the question and decides whether it is a documentation question; "not a documentation question" when it says so; every page of the chosen areas plus the root pages, in a fixed order, with the other areas named as not supplied; "nothing covers it" when no area is chosen; `unknown_area` for an area not in the index; the first area alone when two exceed the budget, and `area_too_large` when the first alone does; the commit as its version; and a fingerprint of the routing prompt, `max-areas-per-ticket`, repository, branch and path. Add the routing prompt as an `analysis_prompt` type and a canned routing answer to `StubChatModel`. Verify each scenario of the GitHub source spec with unit tests, and that changing the routing prompt or `max-areas-per-ticket` changes the fingerprint.

## 4. Analysis run

- [ ] 4.1 Add a migration for `doc_analysis` and for the `analysis_prompt` type holding the classification prompt from 1.2. Add the new table's columns to `service/src/test/resources/erasure-compliance.yaml`. Verify `ErasureComplianceTest` passes.
- [ ] 4.2 Add a `ThreadService` method that returns the thread with a role label on each message (`[bot]`, `[tenant]`, `[support]`; rules in design Decision 7), applying the existing sanitisation (ADR-005) before the label, and leave `getThreadAsText` unchanged. Verify with unit tests for a bot message, a support reply, a ticket raised by a support engineer, a reply from outside the support team, and that the existing classifier's input is unchanged.
- [ ] 4.3 Add the per-ticket classifier against the boundary, following the outcomes table of design Decision 8: fetch the role-labelled thread; ask the source for context within the budget; save `not_applicable` when the source says the thread asks no documentation question, and `missing` when it says nothing covers the question; otherwise run the classification call with the pages the source returned, passing the source's question when it gave one, and parse the structured result, using the provider's JSON-schema output where it has one and accepting a fenced object otherwise. Record a failed attempt with its reason code for each failing row of the table, including a source failure and a source that returns more than the budget. Compute `prompt_id` from the classification prompt, `max-input-tokens` and the source's fingerprint. Pass `question`, `answer_summary` and `rationale` through the sanitisation patterns before saving. Extend `StubChatModel` with a canned classification answer. Verify with unit tests that use the stub source, for each row of the outcomes table and each reason code, for a quote that differs from the page only in line breaks and emphasis markers, for a fenced answer, for stored text that matches a sanitisation pattern, for a source that has no areas, for a source that gives no question, and that a change of fingerprint changes `prompt_id`.
- [ ] 4.4 Add the run: open the documentation source, failing the run when it is unavailable; find the window's closed tickets that are due (no row for the current `prompt_id`, or a failed row past the retry delay with attempts left), classify them one at a time with `llm.request-delay` between calls, and save each result as it completes. Handle failures as design Decision 9 describes: retry a provider failure up to three times with increasing waits; record any other failed ticket with its time, reason code and attempt count and continue; stop the run after five provider failures in a row, removing those failures and holding off new runs for `run-retry-delay`; stop at `max-tickets-per-day`. Hold its own `async_job` row, and run on its own single-thread, no-queue executor (design Decision 4), created only when the feature is enabled. Resume it on startup. Verify with tests for resume, for a failed ticket, for a visit inside and after the retry delay, for a ticket out of attempts, for a provider error that passes on retry, for an outage, for the daily limit, that a Support Summary refresh can start while it runs, and that it can start while a Support Summary refresh runs.
- [ ] 4.5 Add `GET /documentation-analysis` (results, counts, the groups by cited page and by product area, progress, the stopped and daily-limit states, each result's documentation version, and the source's current version and last refresh), returning only results with the current `prompt_id` and counting each ticket under one product area as design Decision 11 describes and `GET /documentation-analysis/enabled`, with the window rules of `/summary`. Restrict the results endpoint to leadership and support engineers in `SecurityConfig`. Verify with controller and security tests.
