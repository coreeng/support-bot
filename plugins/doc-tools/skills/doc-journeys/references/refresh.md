# Refresh and update

Documentation authored by this skill goes stale the moment its sources move on. This file specifies how a later run updates it.

Refresh is **not** "run authoring again and overwrite". Two properties make that approach actively harmful:

1. **Generation is non-deterministic.** Regenerating an unchanged page produces differently-worded prose that says the same thing. Do that across a product and you get a large diff containing a handful of real changes, which no reviewer can usefully review. Churn destroys trust in the output faster than staleness does.
2. **Human review is the most valuable input the docs receive.** A page a human corrected is better than anything this skill can produce. Overwriting it discards the one thing in the system that had a human check it.

So the governing rule is:

> **Change a page only when its evidence changed, and change only what the evidence requires.**

## Frontmatter this depends on

Refresh is only possible because `author` runs record provenance. Every generated page carries this in its `doc_journeys:` block (schema in `${CLAUDE_PLUGIN_ROOT}/skills/doc-journeys/references/output.md`):

```yaml
doc_journeys:
  generated: true
  generated_at: 2026-07-28
  generated_by: claude-opus-5
  skill_version: 2
  content_hash: sha256:3f9a1c...        # of the page body, excluding frontmatter, as written
  sources:
    - repo: foglight-agent
      path: docs/forwarding.md
      repo_head: 9d4b71e...             # source repo HEAD at generation time
      relevance: high
      contributed: the forwarder configuration keys and the restart step
  reviewed:                             # present only once a human has signed off
    by: a.reviewer
    at: 2026-08-04
    at_content_hash: sha256:3f9a1c...
```

If a page lacks `content_hash` (generated by an older skill version), treat it as **human-edited** — the conservative assumption. Never assume a page is safe to overwrite because you cannot tell.

**Section furniture is out of scope for this whole file.** The top-level indexes and the per-product bucket indexes (`tutorial/_index.md`, `how-to/_index.md`, `reference/_index.md`, `explanation/_index.md`) carry no `doc_journeys:` block by design — see `${CLAUDE_PLUGIN_ROOT}/skills/doc-journeys/references/output.md`, *Bucket sections*. They are not human-edited pages, they are not skill-owned pages, and they are not refreshed: their body is a fixed template and their child list is computed by the site at render time. Do not hash them, do not protect them, do not report them as human-edited, and do not offer sidecar proposals for them.

## Step 1 — Did a human edit this page?

Hash the page body as it currently sits on disk, excluding frontmatter, using the same normalisation the generator used. Compare to the recorded `content_hash`.

  * **Match** → the page is exactly as generated. Skill-owned. Safe to regenerate.
  * **Differ** → a human has edited it. Human-owned. Protected for the rest of this run.
  * **`content_hash` absent** → treat as human-owned, unless the page is section furniture (above), which is not assessed at all.

This is the only reliable signal. `generated: true` says who wrote it originally, not who has touched it since — do not use it for this decision.

Git is a useful review surface for the resulting diff, but do not use git history to make this determination. It cannot distinguish a human edit from a previous skill run, and it is wrong whenever changes are uncommitted.

## Step 2 — Did the sources actually change?

For each source repo cited by the page, compare the recorded `repo_head` against the repo's current HEAD:

```bash
git -C <source-repo> rev-parse HEAD
git -C <source-repo> diff --name-only <recorded_head>..HEAD -- <cited paths>
```

The page's evidence is **changed** if any of these hold:

  * a cited file appears in that diff
  * a cited file no longer exists
  * discovery finds a **new** candidate at relevance `high` that is not in the recorded source list — where **new means the file did not exist, or was not high-relevance, at the recorded `repo_head`** (check with `git -C <source-repo> log --oneline <recorded_head>..HEAD -- <path>`, or `git cat-file -e <recorded_head>:<path>`). A high-relevance file that already existed at the recorded head and was simply not cited is a **discovery miss by the previous run**, not changed evidence: the page stays `current`, and the miss is reported under *Suggested actions* with the file named, so a human (or a `force` run) can pull it in deliberately. Without this distinction the same page flips between `current` and `regenerated` from run to run on identical evidence, because term expansion is non-deterministic and a different term set surfaces different uncited files.

That third condition is the one that matters most for your case: a month later, the interesting change is usually new material that did not exist before, not edits to files already cited. **Always re-run discovery on refresh.** Never refresh purely by re-hashing the previously recorded source list — that can only ever find edits to what you already knew about.

Fallbacks when the git comparison is unavailable — `repo_head` not recorded, SHA unreachable after a force-push, shallow clone, repo removed:

  * repo missing entirely → treat evidence as changed, and record the missing repo as a finding
  * SHA unreachable → fall back to comparing current file content against what the page cites; if that is inconclusive, treat as changed

When in doubt, treat evidence as changed. The cost is a regenerated page; the cost of the opposite error is silently stale documentation.

## Step 3 — The decision table

| Human edited | Evidence changed | Force flag | Action |
| --- | --- | --- | --- |
| No | No | No | **Leave untouched.** Report as `current`. Do not rewrite, do not reformat, do not bump `generated_at`. |
| No | Yes | — | **Regenerate in place**, minimal-diff per Step 4. |
| No | No | Yes | **Regenerate in place**, minimal-diff. Used when the model or skill version changed and you want the output redone anyway. |
| Yes | No | — | **Leave untouched.** Report as `human-owned, current`. |
| Yes | Yes | — | **Do not touch the page.** Write a proposal to the sidecar path below and report the diff for a human to merge. |
| Yes | — | Yes | Same as above — a force flag never overrides human ownership. |

**A force flag never overwrites a human-edited page.** There is no invocation that causes this skill to discard a human's edits. If a human wants a page regenerated from scratch, they delete it and re-run; that is an explicit act, and it is theirs to take.

### Sidecar proposals

When a human-owned page has changed evidence, write the newly generated version to:

```
<proposals_root>/<product-slug>/<page-path>.md
<proposals_root>/cross-product-journeys/<page-path>.md
```

Cross-product journey pages take the second form. They belong to no product, so `cross-product-journeys` occupies the slot a product slug would — mirroring the content tree, where the two sections are peers.

`proposals_root` (consumer settings) sits outside the site's content directory, so proposals never publish. The report lists every proposal with a summary of what changed in the evidence and what the proposal changes on the page, so a human can merge the parts worth merging.

Proposals from a previous run that are still present are overwritten — the newest proposal for a page supersedes the older one. Say so in the report.

## Step 4 — Minimal-diff regeneration

When regenerating a skill-owned page, do **not** author it from a blank page. Start from the existing page and apply only what the changed evidence requires.

  * Keep existing wording wherever the underlying facts are unchanged. Rewording for its own sake is a defect in this mode, however much you prefer your new phrasing.
  * Keep heading structure and ordering unless the change genuinely requires new or reordered sections.
  * Update the specific commands, values, paths, fields, and steps the evidence changed.
  * Add sections for genuinely new material. Remove sections whose subject no longer exists in the sources — and say so in the report, because removal is the change most likely to be wrong.
  * Recompute confidence from the new evidence set. It can go down as well as up; a page whose best source was deleted should say so.
  * Update `content_hash`, `generated_at`, `generated_by`, `skill_version`, and every `repo_head`.

Preserve the `reviewed:` block if present, and mark it stale by leaving `at_content_hash` pointing at the hash that was reviewed. A reviewed page that has since been regenerated is no longer reviewed, and the mismatch between `reviewed.at_content_hash` and the current `content_hash` is exactly what records that. The report flags these as **needs re-review**.

### Judging the diff

After regenerating, compare against the previous version. If the diff is large but the evidence change was small, you have almost certainly rewritten prose gratuitously. Discard it, start again from the existing page, and make the narrow change. A regeneration that touches every paragraph because one default value changed is a failure of this mode, not a thorough job.

## Step 5 — Structural changes

**Journeys added** to the product definition → author fresh, as a normal `author` run.

**Journeys removed** from the definition → the directory is **orphaned**. Do not delete it. Report it with its path and page count so a human can remove it. Deleting published documentation because an input file changed is too destructive to automate.

**Journeys renamed** → this looks identical to "one removed, one added", and the skill cannot reliably tell the difference. Author the new journey, report the old directory as orphaned, and say in the report that the two may be a rename. Let the human decide.

**Variations added or removed** → same rules, at page level within the journey directory.

## Targeting

Refresh accepts a scope. Narrower is better — it keeps diffs reviewable:

  * `refresh` — every product in the definition, then the cross-product journeys
  * `refresh <product>` — one product
  * `refresh <product> journey "<name>"` — one journey
  * `refresh cross-product journeys` — the cross-product section only
  * `refresh where sources changed` — every product, but Step 2 gates every page; pages with unchanged evidence are not touched. The cheapest useful refresh, and a good default for a scheduled run.

The two switches from *Mode resolution* in `SKILL.md` compose with any scope above:

  * **`force`** — the Force column of the Step 3 table. Skill-owned pages within the scope are regenerated even where Step 2 found no evidence change; regeneration is still minimal-diff per Step 4, and rows 5 and 6 are unaffected, so human-edited pages remain untouched and still get proposals.
  * **`only-missing`** — write only pages that do not exist. Every page already on disk within the scope resolves to `current` or `human-owned, current` regardless of what Steps 1 and 2 found, and the report says so, because "your evidence moved and this run deliberately ignored it" is exactly the thing a reader must not have to infer.

They are mutually exclusive; an invocation setting both is a contradiction to resolve with the user, not to reconcile.

A scope covering both sections refreshes the cross-product section **last**, for the same reason `author` writes it last: its pages link into the product sections, and `${CLAUDE_PLUGIN_ROOT}/skills/doc-journeys/references/duplication.md` Rule 2 compares them against whatever those sections now contain.

Refreshing a product without the cross-product section can leave a route pointing at a page that moved. Rule 2 will not catch it — it compares content, not link targets — so a scoped refresh reports every cross-product page whose `routes_to` resolved to a path this run changed, as a follow-up rather than a fix.

Discovery still runs across all source repos regardless of scope — narrowing the scope narrows what gets *written*, not what gets *looked at*, because new evidence for a journey can appear in a repo that journey has never cited before.

## Reporting a refresh

The refresh report replaces the `author` report's "Pages written" section with a per-page disposition table:

| Page | Disposition | Evidence change | Confidence |
| --- | --- | --- | --- |
| `archive-telemetry/s3.md` | regenerated | 2 files changed in `foglight-agent` | high (was medium) |
| `archive-telemetry/syslog.md` | current | none | high |
| `archive-telemetry/_index.md` | proposal written | 1 new source found | medium |

Dispositions: `current`, `regenerated`, `proposal written`, `human-owned, current`, `created`, `orphaned`.

The report must also carry:

  * **Needs re-review** — pages regenerated since their `reviewed` block was recorded.
  * **Proposals** — every sidecar written, with what changed and where to find it.
  * **Orphans** — directories and pages no longer backed by the product definition.
  * **Confidence changes** — any page whose confidence moved, in either direction, with why. A page that dropped from `high` to `low` because its best source was deleted is the single most important line in a refresh report.

A refresh where nothing changed should say so in one line and write nothing. That is a successful run, not an empty one.
